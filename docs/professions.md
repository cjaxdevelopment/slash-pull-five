# Rewound professions directory

`/profs` is part of the existing React/Express application, uses its existing login, CSRF protection, PostgreSQL connection, dark styling, and Heroku hosting. The homepage opens the public professions directory directly. Signed-out visitors see no planner/professions navigation tabs, only an **Officer sign in** link to `/planner`; signed-in accounts retain both tabs. Sign-in copy identifies officer access, with existing account permissions and Eizzo-only character approval unchanged. All routes, including shared raid snapshots, use dark mode only and ignore previous saved theme preferences. Existing `/plans/:id` links continue to open the private planner. Anyone can search recipes, view known providers, and browse character professions without signing in. Account usernames, Discord contacts, main/alt links, and claim records require sign-in. All directory writes, including manual refreshes and item-detail prioritization, also require sign-in and CSRF protection. Automatic fetching continues independently of visitors. No Discord service is connected and no Discord messages are sent.

## Connect Forever

The directory uses Blizzard's live WoW Forever API for **Rewound / US / Normal (ruleset 2) / Horde**. Guilds and characters are realmless. A character is identified by a regional first-name/surname slug such as `frostfire-bolt`; its full display name is **Frostfire Bolt**. The adapter validates the guild name, slug, faction and ruleset before accepting its roster, checks roster guild IDs, and verifies character slugs, rulesets and profession character IDs before saving data.

1. Put `BLIZZARD_CLIENT_ID` and `BLIZZARD_CLIENT_SECRET` in the ignored root `.env` for local work, or the hosting platform's secure environment configuration. Credentials and tokens stay on the server; OAuth tokens are cached in memory and sent in authorization headers.
2. Keep `PROFS_ADMIN_USERNAMES=eizzo` for the existing administrator account. Planner ownership gives no implicit directory authority.
3. Use `PROFS_REGION=us` and `PROFS_GUILD_SLUG=rewound` (the defaults). The game version is always Forever and namespaces are derived from the region: `profile-forever-us` and `static-forever-us`. Retired `PROFS_GAME_VERSION`, `PROFS_PROFILE_NAMESPACE`, `PROFS_DATA_NAMESPACE` and `PROFS_GUILD_REALM` overrides are ignored, so an existing retail deployment can start safely after the upgrade. Normal is pinned to ruleset 2.
4. Stop the local API before CLI commands sharing its embedded PGlite directory. Run `npm run profs:sync` to import the roster. Run `npm run profs:seed -- frostfire-bolt` to fetch a specific real character's professions independently. Neither command fabricates data or establishes account ownership. CLI writes use the configured database; production imports require explicit deployment authorization.
5. Start the application. The worker fetches unfetched roster characters and refreshes the roster and characters hourly. Open `/profs` to follow progress. Unfetched and failed data remain explicitly unknown.

The normal 15-minute manual cooldown applies to roster syncs. Failed refreshes preserve successful snapshots. Synthetic fixtures exist only in tests and the isolated browser-test directory labeled **TEST FIXTURES**. No retail character or recipe is relabeled as Forever.

## Member links and contact

Members request a character link in **My characters**. An allowlisted administrator verifies ownership directly with the member, then approves the request. Public Blizzard lookups and roster membership do not establish ownership. A partial unique database index permits only one approved account per character. Approval records retain the reviewer and review time. Administrators can reject pending links or revoke approved ones. A rejected link can be resubmitted for review.

Character names use class colors from Blizzard's roster/profile class IDs. Class IDs are read from Forever profiles and rosters independently of the planner catalog. Unknown classes remain neutral; failed or incomplete refreshes preserve an existing class. An additive migration queues one roster refresh to backfill older records. Name colors also appear in planner cards, shared compositions, buff-provider lists, member links, and character dialogs.

The directory keeps its main view focused on filters, recipes, and crafters. Sync counts, pending item indexing, upstream backoff, missing-data coverage, and the Forever region/ruleset are available under **Data status**. Character views retain their last successful update, explicit unfetched/unavailable state, and current errors. Exact update times are available by hovering over the compact relative timestamp.

An approved member chooses their main and preferred Discord contact. Other approved characters on the same account show their alt association. Only approved links expose the member’s account/contact alongside characters. Revoking a main link immediately removes its displayed association; members must choose another approved main. Characters without an approved link show no member contact.

## Coverage and search

- **Not fetched:** no successful professions response; coverage is unknown.
- **Data unavailable:** a fetch failed without a previous success; coverage remains unknown.
- **Fetched:** a successful API snapshot exists. Each skill tier separately records whether Blizzard supplied an explicit `known_recipes` array. An omitted array means unknown recipe coverage; an explicit empty array is preserved as such.
- **Refresh failed · cached data:** the last successful snapshot, its recipe index, and timestamp remain available. Failed refreshes never erase known ownership or make the timestamp newer.

Recipe matches mean **reported in the last successful Blizzard snapshot**. A successfully fetched character absent from a recipe’s results is not listed as knowing it in that snapshot; this is not a claim about live game state. Unavailable and unfetched data never means “doesn’t know.” Each character view shows its latest success, age, error, and refresh eligibility. Recipe dialogs show only the known providers, their available member/contact association, and last-success timestamps; they do not list unrelated characters with absent or unknown coverage. Data status and character views retain the coverage information.

Skill-tier browsing uses Blizzard’s returned labels, without inferring tiers from recipe names. Search supports recipe names, crafted-item names, and crafted-item IDs. Recipe IDs are separate from crafted-item IDs. The adapter collects `crafted_item`, faction-specific crafted items, and explicit crafted-item arrays, deduplicating by item ID. It does not mistake reagents for products. Multiple products and recipes with no returned product are supported. Gathering/actions/enchantments are not automatically labeled as craftable items. The remaining item-index count is visible, so item-search coverage is not presented as complete. Search is paginated, with 50 recipe/tier matches per page.

Mapped products use [Wowhead’s official tooltip widget](https://www.wowhead.com/tooltips) with Forever item URLs and `domain=forever` for framed item icons, quality-colored names, and rich tooltips when hovering over either the icon or the name. On directory cards, only the small Wowhead rocket after the item name opens the external item page. Recipe cards use two columns on wider screens and one column on smaller screens. A prominent N crafters control sits at the right of each card. Character names stay hidden until that control is hovered or focused; the preview shows the alphabetized, class-colored full names in a bounded scroll area. Escape, leaving the preview, page scrolling, and resizing dismiss it. Clicking the count opens the full searchable list, including on touch devices. The card background, title, and icon also open that same list; internal title/icon actions support Enter and Space and keep their Wowhead hover tooltips. The rocket uses the official Wowhead favicon (https://wow.zamimg.com/images/logos/favicon-live.png), stored locally at app/client/public/wowhead-rocket.png. Fallback icons also open the crafter modal. The full list is alphabetical, uses a bounded scrolling grid, and offers character/member search when there are more than six providers. Filtering never changes recipe ownership. Item names and profession/expansion metadata share one icon block, with uniform 68-pixel icon frames. Multiple products have separate item links in the dialog. Widget-managed anchors live in isolated DOM containers so its added icons and classes do not conflict with React updates. Cached Blizzard recipe-media icons or profession symbols remain the fallback if Wowhead is blocked or unavailable. When Blizzard supplies no crafted-item ID, the link searches Wowhead by name rather than inventing an item or spell ID; these search links cannot show item tooltips. The widget loads only when the professions page is opened. It never receives Blizzard credentials. Direct links and provider lists continue to work if the external tooltip service is blocked or unavailable.

## Refreshes and operation

Each recipe card has a **Materials** control: hover, keyboard focus, or tap shows cached Blizzard reagent names and quantities. Character profile recipe names show the same tooltip and link to a mapped Wowhead item, or a name search when no product ID is known. Recipe IDs are never substituted for item or spell IDs. Missing reagent arrays, explicit empty arrays, missing quantities, and modified crafting slots remain distinct; incomplete recipes direct visitors to Wowhead for additional choices. Gathering actions may have no reagent details. Materials stay inside the native dialog's top layer when browsing a character.

Migration 010 adds reagent metadata to the existing recipe cache. The existing worker gradually backfills metadata version 2, still at most five recipes per tick. Public materials reads are limited to 120 per IP per minute and can prioritize at most 50 registered recipe IDs in memory; hovering never calls Blizzard directly or creates a character refresh job. The tooltip polls only while waiting for this cached metadata. Cache enrichment preserves successful material data on errors and retains upstream backoff and retry limits. This public cache warming does not grant ownership, contact access, or directory write permissions.

Refreshes enqueue persistent database jobs. Automatic refresh is on by default: `PROFS_AUTO_REFRESH=true` and `PROFS_REFRESH_INTERVAL_MINUTES=60`. The interval is configurable from 15 minutes to one week. The scheduler queues unfetched roster characters immediately, then refreshes each character and the roster after the interval. It also discovers new guild members on subsequent roster imports. Set `PROFS_AUTO_REFRESH=false` to retain only manual refreshes. Scheduling runs while the API process is online; a sleeping or stopped host catches up after it resumes. The worker is independent of whether anyone has `/profs` open.

The worker ticks every 2.5 seconds and runs one refresh job at a time. Automatic jobs refill in batches of at most 25 and occupy at most 90 queue slots. Manual jobs have higher priority, with ten reserved slots and a total queue cap of 100. Each character and the guild roster retain persistent 15-minute manual cooldowns. Web writes have an additional account-based limit of 30/hour. Requests use 15-second timeouts, deduplicated jobs, and 5-minute recovery leases. Interrupted jobs can resume after their lease expires. Rate-limit or temporary upstream failures pause Blizzard requests for 15 minutes, keeping successful cached data intact. Character identity is checked against the roster’s Blizzard ID before replacing its snapshot. Imports and snapshot/index changes commit transactionally.

The worker fetches at most five missing/stale recipe details per tick, including during roster seeding so item indexing is not starved. Optional media adds at most one Blizzard media request per recipe. Successful details and icons are cached for 30 days; an additive metadata version backfills icons for older records. Failed attempts back off for a day and an upstream failure stops the current batch. A page requests priority for its visible recipe IDs in one authenticated batch of at most 50, separately limited to 120 batches/hour per account. Those requests only prioritize stored recipe records; they do not call Blizzard synchronously or create ownership records. Item indexing remains gradual for large lists. Tokens are reused and renewed once on HTTP 401; raw upstream error bodies and secrets are not logged or returned.

Keep the project’s existing **single application instance** deployment model. Job claims and cooldowns use database coordination, but application request rate limits and token caching are process-local; recipe enrichment assumes one worker. Local PGlite now has a process-ownership lock: a second API/CLI fails before opening the same data directory, and a dead process’s lock is reclaimed. Graceful server shutdown cancels in-flight Blizzard requests, leaves interrupted refresh jobs ready for restart, and closes the database after worker activity finishes. Database transfers include the profession scopes, characters, snapshots, recipe mappings, claims, member contacts, and queued jobs. Full hosted PostgreSQL backups remain the production recovery mechanism.

## Live Forever validation

On **November 24, 2026**, authenticated requests using the new adapter verified Rewound's guild ID **228021**, Horde faction, and Normal ruleset **2**. The latest roster returned **80 characters**. A subsequent local import saved **802 distinct learned recipes** from **70 available profiles**; the remaining **10 profiles returned HTTP 404**. Existing account/planner data and legacy retail character records were verified unchanged. Crafted-item indexing continues through the bounded worker. Frostfire Bolt returned Tailoring **216/300** with **98 learned recipes**, Cooking with 4, Fishing with 1, and First Aid with 2. These are observed API snapshots, not a promise of in-game completeness.

Recipe **2396**, Boots of the Enchanter, returned crafted item **4325**, three reagent types with quantities, and a Forever Blizzard icon. Recipe and item IDs remain distinct. Wowhead's public widget maps its Forever environment to `forever`.

API paths:

- `/data/wow/guild/rewound` and `/roster`, namespace `profile-forever-us`.
- `/profile/wow/character/{first-name-surname}` and `/professions`, namespace `profile-forever-us`.
- `/data/wow/recipe/{id}` and `/data/wow/media/recipe/{id}`, namespace `static-forever-us`.

The API remains undocumented. Its observed paths and fields are covered by adapter contract tests. Missing learned-recipe arrays mean unknown coverage; explicit empty arrays remain distinguishable. Character 404s preserve cached data and can reflect Blizzard publication delays.

Remaining in-game checks: compare returned skills and recipes against a logged-out character; compare shared and exclusive recipes between two characters; learn a recipe and measure publication delay after the cooldown. Verify crafted-item search and material quantities. Automated tests cover identities, rulesets, failures, ownership, scope isolation, and browser flows.

## Retiring the retail proof of concept

Only Forever is enabled in the runtime adapter. Migration `011_forever_directory.sql` adds regional slugs and pins the guild slug/ruleset without rewriting existing rows. New imports use the separate `forever:us` scope. Legacy realm columns and retail rows are retained for backup compatibility but are neither read into the Forever directory nor refreshed by its worker. Retail character ownership approvals are not transferred to Forever characters. Existing logins and private planner data are unchanged.

## Release

Run `npm run check` and `npm run test:e2e`. The existing root build, `Procfile` release migrations, and Express SPA fallback already serve `/profs`; no new host or domain is needed. Directory migrations through `011_forever_directory.sql` are additive and leave planner tables unchanged. Heroku release configuration, production environment changes, live production imports, and publication require the normal explicit deployment approval. This task does not publish production.

Before release: back up PostgreSQL, configure the hosted runtime’s server credentials and directory administrator, finish the in-game checks, review the migration, and use the repository’s existing Heroku process. After an approved release verify sign-in, `/profs`, the live API connection, private planner isolation, refresh persistence, and read-only share links. A code rollback does not undo the additive migration; retain the new directory tables.
